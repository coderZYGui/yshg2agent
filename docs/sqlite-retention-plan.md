# SQLite 会话数据过期清理方案（保留方案）

## 状态

本方案作为服务器端保存对话历史的备选设计保留，当前不启用。当前项目采用浏览器 IndexedDB 保存对话历史，聊天接口不向 SQLite 写入会话和消息。

## 适用范围

SQLite 方案适合单机、单实例和数据量可控的部署。多实例部署应改用 PostgreSQL 等独立数据库；上传附件应放入对象存储并配置生命周期规则。

## 建议保留周期

| 数据 | 默认保留时间 | 清理依据 |
| --- | ---: | --- |
| 对话和消息 | 180 天 | 会话最后更新时间 |
| 已使用的评审附件 | 30 天 | 文件创建时间 |
| 未关联或上传失败的临时附件 | 24 小时 | 文件创建时间 |
| 知识库文件 | 不自动删除 | 管理员手动删除 |

建议通过以下环境变量配置：

```env
CONVERSATION_RETENTION_DAYS=180
UPLOAD_RETENTION_DAYS=30
ORPHAN_UPLOAD_RETENTION_HOURS=24
CLEANUP_INTERVAL_HOURS=24
```

## 清理流程

清理任务在服务启动时执行一次，之后每 24 小时执行一次：

1. 找出已过期的会话、附件记录和孤立文件。
2. 删除附件实体文件。
3. 删除附件元数据。
4. 删除过期会话；消息通过外键级联删除。
5. 记录本次扫描数量、删除数量、释放空间和失败项，不记录对话正文。

文件删除失败时不删除对应元数据，以便下次重试。数据库记录和文件路径必须限定在应用数据目录内，禁止根据未经校验的路径执行删除。

## SQLite 空间维护

删除记录不会立即缩小 SQLite 文件。建议：

- 日常清理后执行 `PRAGMA wal_checkpoint(TRUNCATE)`。
- 仅在低峰期、完成大量删除且磁盘空间充足时执行 `VACUUM`。
- 对数据库文件和上传目录分别监控容量。
- 磁盘使用率达到 70% 时告警，达到 85% 时拒绝新的附件上传。

## 容量保护

除过期清理外，还需要限制：

- 单次上传最多 10 个附件。
- 单次请求的附件总大小。
- 单个用户或租户的累计容量。
- 上传目录的最大磁盘占用。

只清理 SQLite 记录不能解决附件占用磁盘的问题。清理任务必须同时处理 `backend/data/uploads/` 中的实体文件。

## 恢复该方案时的验收标准

- 过期会话、消息、附件记录和实体文件均被删除。
- 未过期数据和知识库文件不受影响。
- 重复执行清理任务不会报错或误删。
- 大量删除后可在维护窗口回收 SQLite 文件空间。
- 服务日志不包含对话正文、附件内容或访问密钥。
